# Discord目覚ましボット 開発計画

更新日: 2026-09-20

## 現在の利用方針

Mac上でローカルCLIを使い、予約確定時にBotを起動する。予約、音声、通知、操作への応答が完了した後はBotを自動終了する。CLIの全操作とJSON仕様は[ローカルCLI](local-cli.md)を参照する。スキルは別作業で新規作成する。Cloudflareへの配備とD1への移行は保留する。

専用DBでの実機確認では、指定時刻のVC再生、スヌーズ後の稼働継続、取消後の自動終了、音声子プロセスの解放、明示終了を確認した。本番DBの予約は変更していない。CLIの変更操作は操作IDと対象IDを指定し、応答を失った場合は保存済み結果を確認する。

以下は2026-09-19までの仕様と検証記録を保持する。

## 1. 目的と現在地

本人がDiscordのボイスチャンネル（VC）に入って寝ている間に、指定した時刻にYouTubeの曲で起こす。
個人用Botとして作る。Cloudflare ContainersとD1を使う構成を実装したが、有料契約を見送るためデプロイを保留している。既存のサーバーや常時起動できるPCはないため、カード登録が不要な無料のリモート環境を探す。

本書の「確定仕様」は利用者と確認済みである。
コマンド名、技術構成、状態処理は今回採用した構成として実装した。
試験用BotによるDiscord接続、VCへの入退室、メッセージ送信を確認した。YouTube音声の単発再生と、予約後にBotを再起動して指定時刻に再生する動作をMacで確認した。利用者がVCで音声を聞き、停止ボタンで終了できた。リモート環境と就寝中の常時稼働は実機検証を待っている。

## 2. 確定仕様

| 項目 | 内容 |
| --- | --- |
| 利用者 | 自分専用。初期運用は1つのサーバー |
| 稼働場所 | カード登録が不要な無料リモート環境を調査中。Cloudflare Containersへのデプロイは保留する。就寝中の稼働が必要 |
| 予約 | 1回限りの予約を1件保持する |
| 新規登録 | 前の予約を置き換え、変更前後を確認画面に表示する |
| 時刻指定 | 時刻だけを入力し、次に来るその時刻に鳴らす。日付も確認表示する |
| 音源 | YouTube動画の音声を再生する |
| 曲の指定 | 初回はURLを指定する。以降は省略すると前回の曲を使う |
| 再生先 | 発火時に本人がいるVC。本人がVCにいなければ通知だけで終了する |
| 音源の失敗 | YouTube音声を再生できなければ、内蔵アラーム音で鳴らす |
| 再生時間 | 曲を繰り返し、停止・スヌーズ・最大15分のいずれかで終了する |
| スヌーズ | 操作から5分後に再び鳴らす |
| 通知先 | アラームを登録したテキストチャンネル |
| 停止操作 | 通知の停止ボタン。再生中の本人のVC移動・退出でも停止する |
| 停止からの復旧 | 予定から3分以内の遅れなら鳴らし、それより古ければ通知だけで終了する |

内蔵音へ切り替わった場合も、繰り返しと停止の条件は同じにする。
初期版の完成には、YouTubeの音声をVCで再生できることが必要である。

## 3. 採用した初期値と条件

次の設定は今回の実装で採用した。環境変数から設定値を変更できる。

| 項目 | 採用値 | 運用上の確認 |
| --- | --- | --- |
| タイムゾーン | `Asia/Tokyo`を初期値とする | IANAタイムゾーン名を指定可能。夏時間の欠落・重複を自動テストで確認 |
| 音量 | 初期値35%、1〜100%を指定可能 | 実際のDiscord端末で聞こえる音量を試す |
| スヌーズ回数 | 元のアラームにつき最大3回 | 0〜10回を指定可能 |
| 15分の計測 | 最初に音声がPlayingに到達してから15分 | スヌーズ後は新しく15分を計測する |
| 再生準備中・再生中の新規登録 | 停止してから登録する | 停止後に新しい確認画面を開く |
| 実行途中の異常終了 | 中断扱いで通知し、自動再生しない | まだ待機中の予約だけ180秒以内の遅れを許容 |
| YouTube取得待ち | 再生開始前と音声が止まった後の音源待ちは、それぞれ最大15秒にする | 起床時刻からの遅れと成功率を実機で確認する |
| 音声接続待ち | 最大15秒で失敗として終了 | 接続できない場合は内蔵音も送れない |
| 試聴 | 最大30秒 | 1〜120秒を指定可能。寝る前に音量と曲を確認する |
| 動画の対象 | ログイン不要の通常動画 | ライブ、プレイリスト、年齢制限付き動画は対象外 |
| 登録時の取得失敗 | 変更を確定せず、元の予約を保持 | 動画情報の取得に失敗した場合は再度登録する |

曜日の繰り返し、通常の音楽プレーヤー、複数予約、公開Bot向けの管理機能は初期版の範囲から外す。

## 4. 操作案

すべて指定サーバー内のスラッシュコマンドとして提供する。

| コマンド | 用途 |
| --- | --- |
| `/alarm set time:07:30 url:...` | 曲と時刻を指定して予約する |
| `/alarm set time:07:30` | 前回の曲を使って予約する |
| `/alarm show` | 現在の予約と直近の結果を表示する |
| `/alarm cancel` | 待機中の予約を取り消す |
| `/alarm test` | 前回登録した曲を、現在のVCで試聴する |
| `/alarm stop` | 準備中・再生中のアラームを停止する |
| `/alarm snooze` | 再生中のアラームを5分後に延期する |

再生通知には「停止」と「5分スヌーズ」のボタンを付ける。
通知の送信に失敗した場合も、コマンドから停止できるようにする。

### 登録と置き換え

1. 設定済みの本人・サーバーからの操作か確認する。
2. 時刻を`HH:mm`として検証し、タイムゾーンに従って次の日時を求める。
3. URLの指定があれば検証する。省略時は前回登録した曲を使う。
4. 次回日時、タイムゾーン、曲、通知先を表示する。予約があれば変更前後も示す。
5. 本人が確定したら、予約と前回の曲を同じDBトランザクションで保存する。
6. 成功後に予約ID付きの登録結果を表示する。

23時に`07:30`を入力すると、翌朝7時30分の予約になる。
入力時点でその日の指定時刻を過ぎていれば翌日を使う。
同じ時刻ちょうどの入力は翌日とし、秒を指定する操作は設けない。
確認待ちの間に予定時刻を過ぎた場合は、新しい日時を表示して再確認する。

初回のURL省略は入力エラーとする。
「前回の曲」は最後に登録が成功したURLを指し、予約の終了・取消し後も保持する。
スヌーズには、そのアラームに保存した曲を引き継ぐ。

確認画面が保持する予約IDと版が現状と一致した場合だけ、置き換えを確定する。
元の予約が発火済み、または別の予約へ変更済みなら、最新状態を表示してやり直す。
検証失敗、確認の取消し、DB保存失敗では、既存の予約と曲を保持する。

## 5. 発火と音声の制御案

### 発火の流れ

1. Discordの接続復旧後に、時刻を迎えた待機中の予約を取得する。遅延の許容範囲内なら実行開始を記録する。
2. 本人の現在のVCを取得する。
3. 本人がVCにいなければ、未再生として記録して通知する。
4. Botの閲覧・接続・発言権限とVCの空きを確認する。
5. VCへ接続し、本人が同じVCにいることと停止操作が入っていないことを再確認する。
6. YouTube音声を取得する。失敗した場合は内蔵音を選ぶ。
7. 実際にPlayingへ到達した時点で`PLAYING`と開始時刻を保存し、15分の終了タイマーを始める。保存に失敗した場合は音声を停止する。
8. 再生通知と操作ボタンを送り、停止条件を満たすまで繰り返し再生する。
9. 終了時に停止理由と結果を保存して退出する。

開始通知が失敗しても音声再生は続ける。
通知失敗は結果へ残し、`/alarm show`で確認できるようにする。
失敗通知自体も送れない場合は、ローカルログへ記録する。

### 繰り返しと代替音

曲が終わったら、同じ動画を先頭から再生する。
音源取得の失敗に加え、再生途中でYouTube音声が途切れた場合も内蔵音へ切り替える。
内蔵音はFFmpegの音源生成機能で作り、配布音源ファイルを使わない。

代替音へ切り替えた回は、その終了まで内蔵音を使う。
繰り返しや音源の切り替えで15分の終了時刻を延長しない。
内蔵音も再生できなければ、失敗として通知して終了する。

### 停止と本人の移動

`/alarm stop`は、音源取得やVC接続の途中でも受け付ける。
再生通知の停止ボタンも同じ終了処理を使う。
本人が対象VCを移動・退出した場合も、準備中または再生中の処理を停止する。
準備開始後の移動先を自動で追いかける処理は設けない。

終了時は音声、ストリーム、子プロセス、タイマー、VC接続を解放する。
停止後に音源取得が完了しても、終了した実行IDの結果として破棄する。
同時に複数の終了理由が発生しても、終了処理を安全に繰り返せるようにする。

### スヌーズ

スヌーズの受理時刻から5分後を新しい予約時刻とする。
現在の実行を終了状態にする更新と、スヌーズ予約の作成を同じトランザクションで行う。
DBへ保存できてから音声を止める。保存失敗時はスヌーズ成功と表示せず、停止操作は利用可能に保つ。

同時クリックは最初の1回だけ受理し、終了した実行のボタンは無効にする。
スヌーズ後の予約も、通常の予約と同じ1件の枠を使う。
新規予約で置き換えた場合は、前のスヌーズを取り消す。
5分後には本人の現在のVCを取得し直す。

### 試聴

試聴は予約を変更せず、通常の再生と同じ音量・音源取得・終了処理を使う。
本人がVCにいなければ案内する。アラームの準備中・再生中は試聴を開始しない。
試聴中に予約時刻を迎えた場合は、試聴を終了してアラームを優先する。

## 6. 永続化と再起動の設計案

D1へ、前回の曲、予約ID、予定日時、通知先、状態、スヌーズ回数、実行結果を保存する。ローカル開発ではSQLiteを使用する。
予定日時はタイムゾーン付きで確認表示し、検索用の時刻はUTCで持つ。
有効な予約は本人につき1件という制約をDBでも守る。

| 状態 | 意味 |
| --- | --- |
| `WAITING` | 通常予約またはスヌーズの待機中 |
| `STARTING` | 実行権を取得し、音源や音声接続を準備中 |
| `PLAYING` | 音声を再生中 |
| `FINISHED` | 停止・時間切れ・スヌーズなどで終了 |
| `CANCELLED` | 取消しまたは予約の置き換えで終了 |
| `SKIPPED` | 本人の不在や遅延超過で未再生 |
| `FAILED` | 権限・接続・音源などの失敗 |
| `INTERRUPTED` | 実行途中でプロセスが終了した |

終了理由は状態と別の項目で保存する。
スヌーズ元の予約IDと回数を保持し、回数制限を再起動後も計算できるようにする。

### 二重実行の防止

DBトランザクション内で`WAITING`から`STARTING`へ更新できた処理だけが再生を進める。
OSの排他ロックでBotプロセスを1つに制限する。
予約IDを使って操作対象を確認し、古いボタンや遅れて返る非同期処理が新しい予約へ作用することを防ぐ。

Discordへの音声出力とDB更新を同時に確定できない。
このため、中断した再生について「必ず1回だけ聞こえる」という保証は置かない。

### 再起動時の扱い

| 再起動時の状態 | 処理案 |
| --- | --- |
| 未来の`WAITING` | 保存済みの日時まで待つ |
| 予定から180秒以内の`WAITING` | 遅延実行する |
| 予定から180秒を超えた`WAITING` | `SKIPPED`にして通知する |
| `STARTING`または`PLAYING` | `INTERRUPTED`にして通知し、自動再生しない |
| 終了済み | 再生を開始しない |

遅延の判定時刻は、Discordへの接続復旧後に実行権を取得する時点とする。
起動時だけでなく、通信が復旧したときも待機中の予約へ同じ条件を適用する。
スヌーズも保存済みの予定時刻から遅延を判定する。

この方針では、実行開始をDBへ記録した直後に異常終了すると、音を鳴らせないまま予約を終了する可能性が残る。
再生済みの音を再起動で繰り返すことを避けるため、利用者が今回採用した。

## 7. 技術構成と運用の案

| 部分 | 候補と責務 |
| --- | --- |
| 実行環境 | Cloudflare ContainersのNode.js 24とTypeScript。単一プロセス |
| 管理 | Workerの認証付きAPIと固定名のDurable Object。稼働フラグとwatchdogを保持する |
| Discord操作 | `discord.js`。コマンドとボタン、本人のVC状態を扱う |
| 音声接続 | `@discordjs/voice`。DAVE対応を含めて実機で確認する |
| YouTube取得 | `yt-dlp`。音声の取得先を発火時に解決する |
| 音声変換 | FFmpeg。停止時に子プロセスも終了する |
| 永続化 | D1。Containerから仮想ホストの内部API経由で操作する |
| 時刻処理 | 定期的にDBを確認するスケジューラと、単独で検証できる日時計算 |
| 再生制御 | 現在の音声セッションを1つ保持し、停止とスヌーズをまとめて扱う |

Node.js 24.14.1、`discord.js` 14.27.0、`@discordjs/voice` 0.19.2で読み込みと型チェックを確認した。
`yt-dlp` 2026.8.19と`yt-dlp-ejs` 0.8.0を、リポジトリ内のPython環境へ固定して導入した。
JavaScript実行にはDeno 2.7.4を使用する。
参照: [音声ライブラリ](https://discord.js.org/docs/packages/voice/main)、[yt-dlpの依存関係](https://github.com/yt-dlp/yt-dlp#dependencies)。

Botは指定した本人のIDとサーバーIDに限定し、ボタンでも操作権限を確認する。
本人のVCを追跡するため、`GuildVoiceStates`を使用する。
Botには通知と音声接続に必要な権限を与え、AdministratorやMove Membersは要求しない。
満員・権限不足・VC削除で接続できなければ通知して終了する。

URLは許可するホスト名と動画IDを検証し、正規化して取得処理へ渡す。
利用者のURLをシェル文字列へ展開せず、子プロセスには固定した引数構成を使う。
既存の`yt-dlp`設定を勝手に読み込ませず、Google認証情報と恒久的な音声保存は扱わない。
一時的なメディアURL、Token、CookieをログやDBへ保存しない。

YouTubeの利用条件は、コンテンツの利用や自動アクセスを制限している。
技術的な再生成功と利用許諾は分けて扱う。
参照: [YouTube利用規約](https://www.youtube.com/static?template=terms)、[APIポリシー](https://developers.google.com/youtube/terms/developer-policies)。

常時運用ではContainerの稼働状態、再起動後のBot起動、Discord端末の音量を確認する。
受話をミュートした端末でも起こせるという前提は置かず、実際の就寝環境で試聴する。
Bot TokenはWorker SecretからContainerの環境変数へ渡す。D1のエクスポートと復元を確認する。

### リモート状態と更新

初期版は固定名のDurable Objectを1つ使用し、`max_instances=1`とする。公開Workerは管理`start`、`status`、`stop`だけを受け付け、D1操作とContainerへの汎用転送を公開しない。`status`はContainerを起動しない。管理`stop`は稼働フラグを消し、watchdogの再起動を止める。起動失敗時はwatchdogが間隔を置いて再試行する。

内部APIの版を`1`に固定し、異なる版は拒否する。更新は管理`stop`、D1のエクスポートとmigration、deploy、`status`、`start`の順に行う。D1の変更応答を確認できない場合はBotの新規処理と音声を止めて終了する。変更要求は自動再送しない。再起動時に`STARTING`と`PLAYING`を`INTERRUPTED`へ移し、`WAITING`だけ予定から180秒以内なら処理する。状態確認は`/alarm show`を使用する。

ローカルSQLiteは元DBを残して停止中にSQLへエクスポートする。D1へ適用する前に移行先が空であることを確認する。D1のエクスポートと復元はSQLiteのバックアップとは別の手順とする。

## 8. 実装の順序

| 段階 | 内容 | 終了条件 |
| --- | --- | --- |
| 0. 音声の技術検証 | 使用端末と依存関係を確認し、YouTube音声と内蔵音をVCへ送る | DAVE環境で両方が聞こえ、停止後に子プロセスが残らない |
| 1. 予約と保存 | 時刻入力、曲の引き継ぎ、確認、置き換え、表示、取消しを作る | 再起動後も予約と前回の曲が残る |
| 2. 発火と終了 | 本人のVCで再生し、繰り返し・代替音・停止・移動時終了を作る | 決めた条件で鳴り、15分以内に終了する |
| 3. スヌーズと復旧 | 5分後の予約、同時操作、再起動、遅延超過を扱う | 重複予約を作らず、復旧条件どおりに動く |
| 4. 就寝環境での試験 | Cloudflare上のBotと実際に聞く端末で運用する | 下記の必須検証を通し、起動と復元の手順を残す |

段階0でYouTubeの直接再生が成立しなければ、その理由を記録して方式を再検討する。
内蔵音だけの成功を、YouTube再生を含む初期版の完成とは扱わない。

## 9. 必須検証と完成条件

自動検証と媒体取得の技術確認を進めている。Discordへの接続、VCへの入退室、YouTube動画1本の音声再生は確認済みである。アラーム全体の実機検証は未実施である。

### 自動検証

- 日付をまたぐ時刻指定と確認中の時刻経過を確認する。
- URL省略時の曲の再利用と、入力失敗時の既存予約の保持を確認する。
- 古い確認画面、同時の登録、発火と置き換えが重なっても予約が増えないことを確認する。
- 再起動後の復元と、遅延が180秒の直前・一致・直後にある場合を確認する。
- 停止・スヌーズの同時操作と、終了後に返る音源取得結果を確認する。
- 代替音への切り替えと曲の繰り返しで、15分の終了時刻が延びないことを確認する。
- DB保存失敗やプロセス終了後の状態が、採用した復旧方針と一致することを確認する。

時刻処理は時計を差し替えて検証し、数時間の待機を必要とするテストを増やさない。

### Discord実機検証

- 本人以外のコマンド・ボタン操作を拒否できる。
- 時刻と曲を登録し、指定時刻に本人のVCでYouTube音声が聞こえる。
- 動画の終了後に先頭から繰り返し、再生中の失敗では内蔵音へ切り替わる。
- 取得時の失敗でも内蔵音が鳴り、停止と最大15分の条件が働く。
- 本人がVCにいなければ通知だけになり、準備中・再生中の移動でも終了する。
- ボタンとコマンドで停止・スヌーズでき、再起動後も5分後の予約が残る。
- 古いボタンで新しい予約を停止・変更できない。
- 試聴中に予約時刻を迎えると、アラームが優先される。
- 通知権限が失われても音声は鳴り、コマンドで停止できる。
- 満員、接続権限不足、VC削除は音声成功と記録されない。
- 終了後に音声や子プロセスが残らず、BotがVCから退出する。
- 就寝中の稼働、再起動からの復旧、DBバックアップからの復元を確認できる。

初期版の完成は、確定仕様の動作とこれらの必須検証で判断する。
未決事項の採用結果と技術検証で分かった制限は、本書へ反映する。

## 14. 無料リモート環境の候補

2026-09-19時点の公式資料とChrome上の画面を確認した。既存の常時稼働端末はなく、カード登録と有料契約が不要な環境を探す。
