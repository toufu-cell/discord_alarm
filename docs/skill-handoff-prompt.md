# Discord目覚ましBotとスキルの実装依頼

更新日: 2026-09-20

以下を実装担当のエージェントへ渡してください。旧スキルは利用者が削除済みです。新規作成として扱ってください。
Bot側のCLIと自動終了は実装済みです。実際のコマンドと結果は[ローカルCLI仕様](local-cli.md)を参照してください。スキルは別作業で新規作成します。以下は元の依頼文を記録として保持します。

---

Discord目覚ましBotが起動から終了までを管理し、スキルはBotのCLIを呼ぶ構成にしてください。
Bot側のCLIを先に実装・検証し、その公開仕様に合わせて`discord-alarm`スキルを新規作成してください。

## 目的

利用者はこのMacを起動しておく前提です。ターミナルを開かずに「明日7時にこの曲で起こして」と依頼できるようにします。
予約後はエージェントが終了してもBotが動き続け、アラームが最終的に終了したらBot自身も終了する形にします。
PCの電源、ログイン状態、スリープしないこと、ネット接続、利用者のDiscord VC入室が動作条件です。

## 役割分担

| 担当 | 責任 |
| --- | --- |
| Botリポジトリ | CLI、設定、入力検証、予約の確認・保存、日時処理、バックグラウンド起動、二重起動防止、状態確認、再生、スヌーズ、終了、診断 |
| スキル | 自然言語から操作と引数を選ぶ、不足情報を聞く、CLIが返す予約案を利用者へ示す、CLIを呼ぶ、結果を伝える |
| 呼出し元GUI | 利用者の入力をエージェントへ渡し、応答を表示する |

スキルからOSのサービス管理、PID操作、DB読書き、ログ解析、依存の探索を直接行わないでください。それらはBot側の責任です。
起動前のBotに代わってプロセスを用意する起動処理も、Botリポジトリに置きます。
呼出し元は依頼終了時に子プロセスを終了させるため、起動処理はその影響を受けずにBotを稼働させる必要があります。OS機能を使う場合も、方式と設定はBot側へ閉じ込めてください。
作業ディレクトリとPATHは固定とは限りません。呼出し元アプリの変更は不要です。

## Bot側に用意する操作

以下は元の依頼時に列挙した機能です。現在のコマンド名と引数は[ローカルCLI仕様](local-cli.md)を参照してください。

| 操作 | Bot側の動作 |
| --- | --- |
| 予約案の作成 | 日時、YouTube動画、通知先、既存予約との変更点を検証し、確認用の案を返す |
| 予約の確定 | 確認済みの案を保存し、必要ならBotをバックグラウンド起動する |
| 状態確認 | Bot稼働、現在の接続状態、予約、直近の結果を区別して返す。Bot停止中にも使える |
| アラーム停止 | 再生準備中・再生中のアラームを終了する |
| 予約取消 | 待機中の予約を取り消す |
| スヌーズ | 音声を止め、既存仕様の5分後の予約へ移る |
| Bot終了・再開 | 終了では予約を保持して実行プロセスを終了する。再開では保存済みの予約を既存の復旧規則で扱う |
| 診断 | 設定不足や依存の問題を、秘密情報を含めずに返す |

日時、URL、通知先、予約上限などの検証と状態変更は、Discord操作と共通のBot側の処理を使ってください。
スキルは自然言語を引数へ変換しますが、タイムゾーンや期限の最終判定はBotが行います。「明日7時」を、今日の次の7時へ読み替えないよう、明示日付も表現できるCLIにしてください。
Discordのチャンネル情報がないCLI呼出しでは、通知先をBot側の設定か明示引数で解決します。不足時は設定不足を返し、別チャンネルへ勝手に送らないでください。
予約案と確定は別のCLI実行になっても成立させてください。確認期限、日時の経過、確認中に変わった予約、二重送信はBot側で扱い、古い案で新しい予約を上書きしないでください。

## Botの稼働期間

1. 予約確定時、Botが停止中なら起動する。稼働中なら同じBotへ反映する。
2. 待機、再生準備、再生、スヌーズ待ち、試聴の間は稼働を続ける。
3. アラーム停止、上限時間到達、予約取消、失敗、スキップなどで有効な予約がなくなったら、進行中の操作や試聴の完了を待って終了する。
4. スヌーズや新しい予約がある場合は終了しない。終了判定と新規予約が重なっても、予約だけが残って実行されない状態を防ぐ。
5. 終了前に結果保存、必要な通知と操作への応答、音声処理の後始末、VC退出、Discord接続・DB・ロックの解放を済ませる。

アラーム停止後にスキルが別の終了コマンドを送る設計にはしないでください。Discordの停止ボタンから操作した場合も、同じBot側の終了判定を通します。
Bot停止中はDiscordのコマンドを受けられないため、次回の予約はCLI経由で起動できるようにします。稼働中のDiscord操作は引き続き利用可能にしてください。
Botの明示終了は予約取消と区別します。予約が残っていてもBot停止中は鳴らないことを結果へ含めてください。
Botの異常終了時は既存の復旧規則を保持します。終了したアラームをOSの自動再起動の設定で再生し直さないでください。

## スキルの内容

`SKILL.md`は次の内容に絞ってください。

- 起動条件: 目覚ましの予約、状態確認、停止、取消、スヌーズ、Bot終了・再開、診断の依頼。
- 呼出し先: Botの場所、公開CLIの実行方法、操作仕様の参照先。
- 入力: 利用者が指定した日時と曲を渡す。曲の省略可否や前回曲の取得はBotへ任せる。
- 確認: Botが返した予約案を示し、利用者の確定指示を受けて同じ案を確定する。承認済みの同じ内容について再質問しない。
- 結果: CLIの結果を簡潔に伝える。「予約保存済み」「Bot稼働中」「接続未確認」「起動失敗」などを混同しない。
- 曖昧な停止要求: アラーム停止、予約取消、Bot終了の対象を確認する。状態から一意に分かる場合は確認を増やさない。
- 失敗: CLIが返す不足情報や復旧方法を案内する。予約変更の結果が不明なら状態を確認し、同じ変更を無条件に再送しない。

CLIの出力には機械判定できる状態と終了コードを設けてください。文言や過去ログの解析をスキルへ持ち込まないでください。
起動と予約処理は短時間で応答を返し、スキルで予約時刻まで待たないでください。エージェントの終了や取消で処理結果を受け取れなくても、後から状態を確認できるようにします。

## 既存Botの調査で分かったこと

- Node.js 24以上を使い、現在の`npm start`は`node --env-file=.env src/index.ts`を実行する。
- `npm run bot -- start|status|stop`はCloudflare管理用で、ローカル操作には使えない。
- ローカルDBはSQLite。`ProcessLock`が同じDBでの多重起動を拒否する。
- 予約の確認処理は`src/interaction-handler.ts`にあり、確認情報はプロセス内のMapで保持する。新しいCLIとの共通化と、CLI実行をまたぐ確認の扱いが必要。
- `src/time.ts`の時刻入力はHH:mmで、次に来る指定時刻を計算する。明示日付のCLI入力は追加が必要。
- `src/runtime.ts`、`src/playback.ts`、`src/voice.ts`に再生、スヌーズ、停止、後始末がある。現在はアラーム停止後もBotが常駐するため、自動終了の追加が必要。
- `src/index.ts`の起動ログは予約復旧より先に出る。正確な準備状態をCLI側へ返せるようにする。
- 待機予約は180秒以内の遅れなら実行し、準備中・再生中の異常終了は中断扱いにする。音声の取得に失敗した場合は内蔵音へ切り替える。
- 既存の`.env`を保持する。Tokenを会話、引数、生成文書、ログへ転記しない。必要な設定と依存の確認はBot側で行う。

詳細はBotの`README.md`、`docs/plan.md`、`src/`とテストを確認してください。過去のクラウド方針や起動だけを扱う旧依頼より、今回の役割分担を優先します。

## 実装順序と検証

1. BotリポジトリでCLI、共通の予約操作、起動管理、自動終了を実装する。通信方法やファイル構成は既存実装に合わせ、必要な最小構成にする。
2. CLIの操作・出力・失敗時の扱いをBot側で文書化する。
3. skillsプロジェクトで、そのCLIを呼ぶスキルを新規作成する。未実装のBot機能をスキル側で代行しない。
4. CLI単体で「予約・起動 → 再生 → 停止 → Bot終了」が完結することを確認する。
5. スヌーズではBotが終了せず、停止・取消では不要なBotや音声プロセスが残らないことを確認する。
6. 予約置換、二重実行、確定応答の喪失、起動失敗、終了と新規予約の競合で、予約消失や二重再生が起きないことを確認する。
7. GUIから呼んだ後にエージェントやGUIを終了しても予約が実行されることを確認する。今回の端末は`atatapp`のFull Agent Environmentを使う。権限設定は利用者に案内する。
8. 既存テスト、変更に必要なテスト、スキルの構造検証、textlintを実行する。実機検証の未実施項目は理由とともに報告する。

最寄りの`AGENTS.md`と必要なスキルを読み、各プロジェクトの委譲・レビュー・テスト規約に従ってください。
Bot側を変更できない作業環境では、必要なCLI仕様とBot側への依頼を具体化して返してください。スキル側へ起動管理や予約処理を戻して解決しないでください。
完了時はBot側とスキル側の変更、呼出し例、初回設定、検証結果、未完了事項を分けて報告してください。
